## 1. Введение

В современном мире компьютерных игр значительное место занимают так называемые *clicker*-игры — жанр, в котором основной механикой является многократное нажатие на объект для получения внутриигровой валюты. Несмотря на кажущуюся простоту, такие игры позволяют продемонстрировать широкий спектр принципов объектно-ориентированного программирования (ООП): инкапсуляцию, наследование, полиморфизм, композицию и абстракцию.

Цель данной курсовой работы — разработать игру-кликер «Мой карасик» на языке C# с использованием WPF, реализовав авторизацию, прогрессию, магазин предметов и таблицу лидеров с сохранением данных на удалённый сервер.

Задачи работы:
- Изучить принципы ООП и применить их на практике
- Реализовать модель предметной области (карась, звания, шляпы, магазин)
- Реализовать игровую логику (клик, повышение ранга, покупка и надевание шляп)
- Реализовать авторизацию через HTTP API
- Реализовать автоматическое сохранение на сервер
- Построить графический интерфейс на WPF
- Протестировать работоспособность и обработать возможные ошибки

## 2. Теоретическая часть

### 2.1. Жанр clicker: история и описание

Жанр clicker (также известный как idle game или incremental game) берёт своё начало с игры Cookie Clicker (2013), разработанной Julien Thiennot. Основная механика проста: игрок многократно нажимает на объект (печенье, карася и т.д.), зарабатывая валюту. На заработанную валюту можно приобретать улучшения, которые увеличивают доход за клик или автоматизируют процесс.

Математическая модель clicker-игры строится на экспоненциальном росте: с каждым новым уровнем или предметом стоимость следующего улучшения растёт, а доход увеличивается мультипликативно. Это создаёт ощущение прогресса и удерживает интерес игрока.

### 2.2. Основные принципы ООП, использованные в проекте

1. **Инкапсуляция** — каждый класс скрывает внутреннее состояние и предоставляет публичные методы для взаимодействия. Например, класс `Crucian` содержит поля `Currency`, `CurrentRankIndex`, а изменение валюты возможно только через вызов `Click()` или методы `Shop`.

2. **Наследование** — WPF-окна `AuthWindow`, `MainWindow`, `LeaderboardWindow` наследуются от базового класса `Window`.

3. **Полиморфизм** — реализован через делегаты и события. `GameManager` объявляет события (`OnCurrencyChanged`, `OnRankUp`), на которые подписывается `MainWindow`. Один и тот же вызов `Invoke` может вызывать любой метод с подходящей сигнатурой.

4. **Абстракция** — каждый класс скрывает сложность за простым интерфейсом: `ApiClient` скрывает HTTP-запросы и JSON-сериализацию, `SaveManager` скрывает логику сохранения, `Shop` скрывает проверку денег и индексов.

5. **Композиция** — `GameManager` содержит объекты `Crucian`, `Shop`, `SaveManager`, `ApiClient`, управляя их взаимодействием.

### 2.3. Средства разработки — C# и WPF

Проект реализован на платформе .NET 10.0 с использованием:

- **C#** — объектно-ориентированный язык с поддержкой делегатов, событий, async/await, LINQ.
- **WPF (Windows Presentation Foundation)** — фреймворк для построения графических интерфейсов на основе XAML. Позволяет разделить разметку (XAML) и логику (code-behind).
- **HTTP API** — для авторизации, сохранения и загрузки данных используется REST API на базе JSON.
- **System.Text.Json** — встроенная библиотека для сериализации/десериализации JSON.

## 3. Практическая часть

### 3.1. Проектирование программы

Архитектура приложения построена по принципу разделения ответственности (SRP):

```
App (точка входа)
 └── AuthWindow (авторизация)
      └── MainWindow (главное окно)
           ├── GameManager (игровая логика)
           │    ├── Crucian (состояние игрока)
           │    ├── Shop (каталог шляп)
           │    ├── SaveManager (сохранение)
           │    └── ApiClient (HTTP-запросы)
           └── LeaderboardWindow (таблица лидеров)
                └── ApiClient
```

Основные пакеты:
- `Models/` — доменные модели (Crucian, Rank, Hat, Shop, GameManager)
- `Services/` — HTTP-клиент и DTO (ApiClient, AuthResult, UserDataResult, LeaderboardResult)
- `Save/` — менеджер сохранения (SaveManager)
- `assets/` — PNG-изображения (карась + 5 шляп)
- Корень — WPF-окна (App, AuthWindow, MainWindow, LeaderboardWindow)

### 3.2. Модели предметной области

#### Rank (Звание)

Хранит данные об одном ранге: название, количество червячков за клик (`ClicksPerHit`), порог валюты для перехода (`RequiredCurrency`). Статический метод `GetAllRanks()` возвращает список из 10 рангов с экспоненциально растущими требованиями.

| № | Название | Червячков за клик | Порог перехода |
|---|----------|------------------|----------------|
| 1 | Икринка | 1 | 100 |
| 2 | Малёк | 2 | 1 000 |
| 3 | Карасёнок | 16 | 10 000 |
| 4 | Карась-студент | 80 | 100 000 |
| 5 | Бывалый карась | 500 | 1 000 000 |
| 6 | Карась-качок | 2 500 | 50 000 000 |
| 7 | Золотой карась | 5 000 | 250 000 000 |
| 8 | Карась-авторитет | 10 000 | 1 000 000 000 |
| 9 | Великий карась | 25 000 | 5 000 000 000 |
| 10 | Бог пруда | 50 000 | 10 000 000 000 |

#### Hat (Шляпа)

Неизменяемый объект (immutable) с полями: `Name`, `Price`, `Multiplier`, `ImagePath`. Пять шляп с возрастающей ценой и множителем:

| № | Название | Цена | Множитель |
|---|----------|------|-----------|
| 1 | Кепка | 100 | ×6 |
| 2 | Соломенная шляпа | 3 000 | ×8 |
| 3 | Цилиндр | 30 000 | ×12 |
| 4 | Корона | 300 000 | ×20 |
| 5 | Каска | 3 000 000 | ×32 |

#### Crucian (Карась)

Центральная модель, представляющая игрока. Хранит валюту (`Currency`), индекс текущего ранга (`CurrentRankIndex`), общее количество кликов (`TotalClicks`), надетую шляпу (`EquippedHat`) и список купленных шляп (`PurchasedHatIndices`).

Ключевой метод — `Click()`:

```csharp
public long Click()
{
    TotalClicks++;
    double earnings = CurrentRank.ClicksPerHit;
    if (EquippedHat != null)
        earnings *= EquippedHat.Multiplier;
    Currency += (long)earnings;
    return (long)earnings;
}
```

Метод `TryRankUp()` проверяет, достигнута ли валюта порога для следующего ранга, и при успехе увеличивает `CurrentRankIndex`.

#### Shop (Магазин)

Содержит список `AvailableHats` (5 шляп). Основные методы:

- `TryBuy(Hat, Crucian)` — проверяет, хватает ли валюты и не куплена ли уже шляпа; списывает цену и добавляет индекс в `PurchasedHatIndices`.
- `Equip(Hat, Crucian)` — устанавливает `Crucian.EquippedHat`.

### 3.3. Игровая логика (GameManager)

`GameManager` — центральный класс-оркестратор. Создаётся в `MainWindow` и управляет всей логикой:

**Свойства:**
- `Crucian` — объект игрока
- `Shop` — магазин шляп
- `ApiClient` — HTTP-клиент

**События (event):**
- `OnCurrencyChanged(long)` — валюта изменилась
- `OnRankUp(Rank)` — ранг повысился
- `OnHatChanged()` — шляпа надета/снята/куплена
- `OnTotalClicksChanged(long)` — клики изменились
- `OnSaveError(string)` — ошибка сохранения

**Методы:**
- `HandleClick()` — обрабатывает клик: вызывает `Crucian.Click()`, проверяет повышение ранга, оповещает UI через события.
- `BuyHat(int)` — покупка шляпы через `Shop.TryBuy()`, с оповещением UI.
- `EquipHat(int)` — надевание или снятие шляпы.
- `SaveGame()` — асинхронное сохранение через `SaveManager`.
- `SaveOnExit()` — сохранение перед закрытием.
- `StartNewOrLoadGame()` — загрузка данных с сервера при старте.

**Автосохранение:** Timer на 30 секунд проверяет флаг `_hasUnsavedChanges` и при наличии изменений вызывает `SaveGame()` (fire-and-forget).

### 3.4. Сохранение и API-клиент

#### ApiClient

HTTP-клиент для общения с сервером `176.109.110.146:6767`. Все методы следуют одному шаблону:

1. Сериализация тела запроса в JSON
2. Создание `StringContent` с типом `application/json`
3. Отправка POST-запроса через `HttpClient.PostAsync()`
4. Чтение ответа и десериализация из JSON в C#-объект

Эндпоинты:

| Метод | Endpoint | Назначение |
|---|---|---|
| `Register(username, password)` | `POST /api/auth/register` | Регистрация |
| `Login(username, password)` | `POST /api/auth/login` | Вход |
| `LoadUserData()` | `POST /api/auth/loadUserData` | Загрузка данных |
| `SaveUserData(...)` | `POST /api/auth/saveUserData` | Сохранение данных |
| `GetLeaderboard()` | `POST /api/game/leaderboard` | Топ-20 игроков |

DTO-классы: `AuthResult`, `UserDataResult`, `LeaderboardResult`, `LeaderboardEntry`.

#### SaveManager

Делегирует HTTP-запросы `ApiClient`. Метод `Save(Crucian)` сериализует состояние игрока и отправляет на сервер. Метод `Load(Crucian)` загружает данные и восстанавливает состояние, включая надетую шляпу.

### 3.5. WPF-интерфейс

#### AuthWindow

Модальное окно авторизации. Поля: имя пользователя, пароль. Кнопка «Войти» / «Зарегистрироваться» переключается. При успехе сохраняет `ApiClient.Token` и устанавливает `DialogResult = true`.

#### MainWindow

Главное игровое окно. Разделено на 4 строки Grid:
1. **Верхняя панель** (статус-бар): звание, валюта, кнопка «Топ 20».
2. **Центральная область**: кликабельное изображение карася с наложением шляпы. При клике — анимация масштабирования.
3. **Магазин** (скрыт по умолчанию): открывается по кнопке «Магазин» в нижней панели.
4. **Нижняя панель**: общее количество кликов, кнопки «Магазин» и «Топ 20».

Магазин строится динамически в `BuildShopUI()`: для каждой шляпы создаётся Border с изображением, названием, ценой, множителем и кнопкой действия («Купить» / «Надеть» / «Надета ✓»).

#### LeaderboardWindow

Модальное окно с таблицей топ-20 игроков. Данные загружаются асинхронно при открытии через `ApiClient.GetLeaderboard()`. Отображает: место, имя, звание, валюту.

### 3.6. Взаимодействие классов

Последовательность работы приложения:

1. `App.OnStartup()` → открывает `AuthWindow`.
2. Пользователь вводит данные → `AuthWindow.OnActionButtonClick()` → `ApiClient.Register()` или `Login()`.
3. При успехе: `App` создаёт `MainWindow(authWindow.ApiClient)`.
4. `MainWindow` создаёт `GameManager(apiClient)` и подписывается на все его события.
5. `MainWindow.Loaded` → `GameManager.StartNewOrLoadGame()` → `SaveManager.Load()` → `ApiClient.LoadUserData()` — загрузка прогресса.
6. Игровой цикл: клики → `HandleClick()` → обновление UI через события + автосохранение.
7. Покупка шляпы → `BuyHat()` → `Shop.TryBuy()` → списание валюты → `SaveGame()` (fire-and-forget).
8. Закрытие окна → `OnWindowClosing()` → `SaveOnExit()` → `Shutdown()`.

## 4. Тестирование и отладка

### 4.1. Подход к тестированию

В проекте используется ручное тестирование ключевых сценариев:

- **Функциональное тестирование** — проверка, что клик увеличивает валюту, покупка списывает цену, повышение ранга работает.
- **Интеграционное тестирование** — проверка авторизации, загрузки и сохранения данных через сервер.
- **UI-тестирование** — проверка корректности отображения элементов (шляпы, кнопки, анимация).

### 4.2. Примеры игровых тестов

**Тест 1: Клик без шляпы**

Начальное состояние: ранг «Икринка» (ClicksPerHit = 1), шляпа не надета. После одного клика:
- `TotalClicks` = 1
- `Currency` = 1

**Тест 2: Клик со шляпой**

Если надета «Кепка» (множитель ×6), ранг «Икринка»: один клик приносит 6 червячков.

**Тест 3: Повышение ранга**

При `Currency >= 100` (порог для «Малька») и вызове `TryRankUp()`: `CurrentRankIndex` увеличивается на 1, ClicksPerHit становится 2.

**Тест 4: Покупка шляпы**

При `Currency >= 100` покупка «Кепки» успешна: -100 к валюте, шляпа появляется в `PurchasedHatIndices`. Повторная покупка той же шляпы блокируется.

**Тест 5: Недостаточно средств**

При `Currency = 50` и попытке купить «Кепку» (100): `TryBuy` возвращает `false`.

**Тест 6: Авторизация**

При регистрации нового пользователя сервер возвращает токен. Тот же токен используется для загрузки данных.

### 4.3. Обработка ошибок

| Ошибка | Причина | Решение |
|---|---|---|
| Сервер недоступен | Нет соединения с `176.109.110.146:6767` | `ApiClient` перехватывает `HttpRequestException` и возвращает DTO с `Success = false` |
| Истёк токен | Токен недействителен (24 часа) | Пользователь перенаправляется на повторную авторизацию |
| Ошибка сохранения | Сервер вернул `success: false` | `GameManager` генерирует событие `OnSaveError`, UI показывает всплывающее сообщение |
| Пустые поля ввода | Логин < 3 или пароль < 6 символов | `AuthWindow.Validate()` возвращает текст ошибки до отправки запроса |
| Некорректный JSON | Ошибка десериализации | `JsonSerializer.Deserialize` с `PropertyNameCaseInsensitive = true`; при null возвращается DTO-заглушка |

### 4.4. Результаты тестирования

Все ключевые сценарии протестированы вручную:

- **Регистрация и вход** — успешное получение токена.
- **Сохранение и загрузка** — прогресс сохраняется на сервер и восстанавливается при повторном входе.
- **Игровой процесс** — клик, покупка шляпы, надевание/снятие, повышение ранга работают корректно.
- **Автосохранение** — изменения сохраняются при закрытии окна и каждые 30 секунд.
- **Таблица лидеров** — загружает топ-20 игроков.
- **UI** — анимация клика, переключение видимости магазина, обновление кнопок.
- **Обработка ошибок** — при недоступности сервера пользователь получает уведомление, приложение не падает.
